how does a rate limiter actually work? like in simple terms
--- reference
A rate limiter counts how many requests each client sends within a time window and rejects or delays anything above the allowed amount. A popular design is the token bucket: tokens refill at a steady pace, every request spends one, and an empty bucket means the client has to wait. That allows short bursts while still holding the long-run average down, and blocked clients typically get a "too many requests" error.

quick one - what's 'technical debt'?
--- reference
Technical debt is the future cost of shortcuts taken in code or design to ship faster. Like financial debt it accrues interest: the longer it stays, the slower and riskier every later change becomes.

=== J-0079
--- user
p95 latency meaning?
--- reference
p95 latency is the response time that 95% of requests come in under, so it describes the slow end of your traffic rather than the typical case. A p95 far above the average means some users are getting a noticeably worse experience.

=== J-0022

idempotent api - what's that
--- reference
An idempotent endpoint can be called repeatedly with the same input and leaves the system in the same state as a single call. That is why PUT and DELETE are meant to be idempotent, while a plain POST usually is not.
