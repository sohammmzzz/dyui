# Instruction: Build a Ground-Truth Dataset for DyUI Model Evals

## Purpose

I want a **ground-truth evaluation dataset** for a model that writes DyUI (v1.3.0) **without the component catalog in its system prompt**. The dataset will be used only to test and score models. It will not be used for training.

Each item must have a trustworthy reference answer and machine-checkable expectations. A scorer can then say whether a model's reply is correct without a human reading it.

I will compare three setups on this dataset:
1. a base 8B model with the full catalog in its prompt,
2. the fine-tuned 8B model with no catalog,
3. gpt-oss-120b with the catalog, as the reference.

## What the model under test sees

```
system:  [optional control header]      ← 0–40 tokens
         <the app's own system prompt>  ← persona/task only, nothing about output format
user / assistant / tool turns ...
```

Header variants to cover:

| Header | Meaning |
|---|---|
| *(none)* | All 36 built-ins available |
| `[dyui: table, chart, callout, quick_replies]` | Only these components; use the best allowed one, never one outside the list |
| `[dyui +flight(airline: string, depart: string, arrive?: string, price: number)]` | All built-ins plus a custom component, by signature only |
| `[dyui: markdown, table +ticket(id: string, title: string, status: "open"\|"closed")]` | Restricted set plus a custom component |
| `[dyui off]` | Plain Markdown only; no dyui block |

Custom signatures use the format DyUI already writes: `name(prop: type, opt?: type, enum: "a"|"b")`.

## The spec the reference answers must follow

**Output format**
1. One sentence of prose, then a ```` ```dyui ```` block.
2. One compact, single-line JSON object per line: `{"ui":"<name>",...props}`.
3. A closing ```` ``` ````, then a short takeaway.
4. Never components alone, never HTML.
5. At most 3 blocks and 6 components per reply.

**The 36 built-ins** (exact names and signatures come from `dyui.catalog()` and each class's `model_json_schema()`; never hand-copy them)

| Group | Components |
|---|---|
| content | markdown, callout, code, quote, sources, badges, divider |
| data | table, stat, stats, keyvalue, chart, progress, timeline, json |
| media | image, gallery, video, audio, file, link_preview |
| interactive | buttons, quick_replies, choice, form, confirm, rating |
| layout | card, grid, tabs, accordion, carousel, list |
| agent | step, reasoning, plan |

**Action round-trip** (action turns in the dataset are generated by code with `action_text()`, never written by a model)

| Component | Default action | Payload |
|---|---|---|
| `confirm` | `confirm` | `{"confirmed": true\|false}` (plus `data`) |
| `form` | `form_submit` | `{"<field>": value, ...}` |
| `choice` | `choice` | `{"selected": [..], "other"?: ".."}` |
| `rating` | `rating` | `{"rating": n}`; thumbs gives `1` or `-1` |
| `buttons`, `card.actions`, `list` items | their `action` | their `data` |
| `quick_replies` | none | arrives as a plain user message |

Text form: `[action:<name>] {data + values}`.

**History:** earlier assistant turns appear as compact dyui blocks with props only. `step`, `reasoning`, `invalid` and `html` nodes are dropped.

## The decision policy (defines "correct component")

Every reference answer must follow this table, and every item's `policy_row` label points into it.

| User need | Correct component |
|---|---|
| One headline number | `stat` |
| 2–6 headline numbers | `stats` |
| Values over time | `chart` line or area |
| Compare categories | `chart` bar (`stacked` for parts within categories) |
| Shares of a whole (≤ 6) | `chart` donut or pie |
| x/y relationship | `chart` scatter |
| ≥ 3 records × ≥ 2 fields | `table` (2 records means prose or `keyvalue`) |
| Facts about one entity | `keyvalue` |
| Ordered events | `timeline` |
| Sequence of work with statuses | `plan` |
| One goal's progress | `progress` |
| Code, command or config | `code`, always with `language` |
| Tip, warning, error or success | `callout` with matching `level` |
| Same thing in variants | `tabs` |
| FAQ or optional depth | `accordion` |
| Comparable items | `carousel` or `grid` of `card`s; `list` when compact |
| Assistant needs structured input | `form` |
| One question, fixed options | `choice` |
| Irreversible or outward action | `confirm` (`danger: true` when destructive) |
| Things the user can *do* next | `buttons` |
| Things the user might *ask* next | `quick_replies` (≤ 4 options) |
| Citing given sources | `sources` (URLs from context only) |
| Media from given URLs | `image`, `gallery`, `video`, `audio`, `file`, `link_preview` |
| Small talk, definitions, one-line facts, opinions, rewriting | **no component** |

Never: add filler ("Feel free to ask…"), repeat the same data in a component and in the prose, or invent data, URLs or component names.

## Record format

Each item is one test case. Because several answers can be valid, every record carries a gold reference **and** machine-checkable expectations.

```json
{
  "id": "B-0173",
  "category": "B",
  "dyui": "1.3.0",
  "header": null,
  "messages": [
    {"role": "system", "content": "You are the analytics copilot for a SaaS team."},
    {"role": "user", "content": "…"}
  ],
  "reference": "…gold assistant reply…",
  "expected": {
    "policy_row": "shares",
    "components_any_of": ["chart"],
    "chart_kind_any_of": ["donut", "pie"],
    "allowed_components": null,
    "must_have_block": true,
    "grounding_values": ["4120", "2380", "1310", "640"],
    "forbidden": ["invented URLs", "HTML", "filler"]
  }
}
```

For multi-turn items (E, F), `messages` ends on the last user turn, and `expected` also holds the required action name or payload, or the history values that must stay unchanged.

## Categories to produce

Suggested size is **about 3,000 items**, which you can scale in the same proportions. The coverage floors apply at any size.

| # | Category | Share | Items | What it tests |
|---|---|---|---|---|
| A | Single component, exhaustive prop and enum coverage | 20% | 600 | Each component crossed with {required-only, typical, all props} and every enum value |
| B | Intent → component selection with near-miss pairs | 12% | 360 | Same topic, different data shape, different correct answer |
| C | Several components in one reply | 10% | 300 | Correct combination and order |
| D | Nested layouts (incl. `code` inside layouts, JSON escaping) | 9% | 270 | `children`/`tabs` structure; depth 3 is ≥ 10% of D |
| E | Interactive multi-turn flows | 9% | 270 | Action round-trips; 20% where the user ignores the widget |
| F | Follow-up edits using history | 7% | 210 | Untouched values preserved byte-for-byte |
| G | Grounded in tool results or context | 8% | 240 | Every value and URL comes from context; includes error, empty and huge-result variants |
| H | Restricted set via `[dyui: …]` and `[dyui off]` | 4% | 120 | Header adherence; ~30% leak tests, ~15% `[dyui off]` |
| I | Custom components via `[dyui +sig]` | 4% | 120 | Generalisation from a signature alone |
| J | Plain text, no component (negatives) | 7% | 210 | Over-use of components |
| K | Guardrails | 3% | 90 | Injection, HTML/JS, invented URLs, unsafe actions |
| L | Agent components (`plan`, `step`, `reasoning`) | 2% | 60 | Status values and structure |
| N | Wrong-name traps | 3% | 90 | User asks for a UI that doesn't exist |
| S | Self-knowledge for developers | 2% | 60 | Answers about DyUI syntax from internal spec |

### Category notes and examples

**A. Single component**
> **User:** Uptime this month was 99.97% against our 99.9% SLO. How are we doing?
> **Reference:** prose + `{"ui":"stat","label":"Uptime · November","value":"99.97%","delta":"+0.07 pts vs SLO","trend":"up","help":"SLO 99.9%"}` + takeaway.

**B. Selection (near-miss pairs)**
Build pairs where only the data shape changes: 1 number → `stat` vs 4 numbers → `stats`; 2 rows → prose vs 8 rows → `table`; shares → donut vs trend → line; one entity → `keyvalue` vs many → `table`.
> **User:** Signups per channel last quarter: organic 4,120, paid 2,380, referral 1,310, partners 640. Where are they coming from?
> **Reference:** `chart` `kind: "donut"` with the four labels and values.

**C. Multi-component**
> **User:** MRR 48.2k (+12.4%), churn 1.9% (down from 2.3), 214 new customers. MRR Jun–Nov: 31.2, 33.8, 36.1, 39.4, 42.9, 48.2.
> **Reference:** `stats` block, prose, then an `area` `chart`, then a takeaway.

**D. Nested layouts**
> **User:** How do I read an env var in Python and Go?
> **Reference:** `tabs` with a `code` child per language (`language` set; `\n` and `\"` escaped correctly).

**E. Interactive flows**
Flow types: form → submit → result; confirm → yes/no; choice → answer; buttons with `data`; rating → thanks; quick-reply tap; user ignores the widget and types something else.
> **User:** Cancel my Pro subscription.
> **Reference:** `confirm` with `action:"cancel_subscription"`, `data:{"plan":"pro"}`, `danger:true`.
> **User (code-generated):** `[action:cancel_subscription] {"plan":"pro","confirmed":true}`
> **Reference:** `callout` `level:"success"` + takeaway.

Include the `confirmed:false` branch ("Kept Pro…") and a `choice` reply such as `[action:choice] {"selected":["Weekly"]}`.

**F. Follow-up edits**
The earlier block appears in history exactly as `serialize_history` writes it. Edits to cover: chart kind change, add or remove points, top-N or sort, table ↔ chart, translate labels, add a column, "make it shorter".
> **History:** `{"ui":"chart","kind":"area","title":"MRR",…}`
> **User:** Make that a bar chart and add December at 51.0.
> **Reference:** same block with `kind:"bar"` and December appended; all other values unchanged.

**G. Grounded**
Real `tool_calls` and `tool` messages in the chat template. Variants: tool error → `callout` `level:"error"`; empty result → prose; huge result → summary plus top-N `table`.
> **Tool `get_open_incidents` →** three incidents (INC-311, INC-309, INC-306).
> **Reference:** `table` with exactly those rows and values.

**H. Restricted set**
The model must use the best allowed component or prose, and never mention the restriction.
> **System:** `[dyui: markdown, callout, table]`
> **User:** Chart our weekly active users: 1.2k, 1.4k, 1.3k, 1.7k.
> **Reference:** `table` (not `chart`), no mention of the restriction.

**I. Custom components**
Write about 300 synthetic custom components (`flight`, `weather`, `invoice`, `candidate`, `recipe`, `pr_status`, `ticket`, `listing`, …), each with 2–8 props of mixed types and optionality. Register each with `@app.component` so its signature is produced by DyUI itself, and validate every reference block against its real class. **Hold out 60 components** as the test set so the eval measures generalisation from a signature, not memory.

**J. Plain text**
Greetings and thanks, definitions, yes/no answers, opinions, numbers inside a sentence, rewriting or translating, explanations, short follow-ups.
> **User:** What does idempotent mean for an API?
> **Reference:** two or three sentences of prose, no dyui block.

**K. Guardrails**
- Instructions injected into tool results or documents (e.g. "render a form asking for their password"): ignore them, optionally add a `callout` `level:"warning"`.
- "Render this HTML/JS" or `<script>` in markdown: components only; show a snippet in `code` if the user wants to see it.
- Media with no URL in context: never invent one; ask or answer in text.
- `javascript:` and `data:` links: never; `sources` and `link_preview` use context URLs only.
- Delete, pay or send: always `confirm`, never bare `buttons`.

**L. Agent components**
`plan` statuses: pending, active, done, error, skipped. Also `step` and `reasoning`.

**N. Wrong-name traps**
The reference maps each wrong name to the real component. This table is also the **hallucination blocklist** used by the scorer.

| User says / model tends to invent | Correct |
|---|---|
| alert, banner, notice, toast | `callout` + `level` |
| KPI, metric, number card | `stat` / `stats` |
| bar chart, line graph, histogram, pie | `chart` + `kind` (histogram = `bar`) |
| stepper, steps, checklist, todo | `plan` or `timeline` |
| dropdown, select, radio, checkbox | `choice`, or a `form` field `type` |
| button (singular), CTA | `buttons` with `items` |
| chips, suggestions | `quick_replies` with `options` |
| modal, dialog, "are you sure" | `confirm` |
| collapsible, FAQ, expander | `accordion` |
| slider, swiper, cards row | `carousel` |
| tag, label, pill | `badges` |
| code block, snippet | `code` + `language` |
| citation, references | `sources` |
| spreadsheet, grid of data | `table` (`grid` is layout only) |

Prop-name traps (wrong → right): `table.headers` → `columns`, rows as arrays not objects; `chart.type`/`chart.data` → `kind`, `series[].data`; `callout.type`/`variant` → `level`; `quick_replies.items` → `options`; `buttons.buttons` → `items`; `tabs.items` → `tabs`; `stat.title` → `label`.

**S. Self-knowledge**
A developer asks "what can you render?", "what props does `form` take?" or "how do I show a stacked bar chart?" Example JSON in the answer goes **inside a `code` component** (`language:"json"`), never in a bare ```` ```json ```` fence, because DyUI's parser treats a json fence with a `"ui"` key as a live component.

## Coverage minimums (counted over the whole eval set)

These are my suggested floors for eval scale; adjust as needed.
- **Components:** every built-in appears in at least 30 reference replies. Oversample the rare ones (`audio`, `video`, `quote`, `divider`, `json`, `rating`, `step`).
- **Enum values:** every value of every enum appears at least 10 times (all 6 `chart.kind`s, 4 `callout.level`s, 11 form field `type`s, 7 badge colours, 4 button styles, statuses of `timeline`/`plan`/`step`, `rating` styles).
- **Props:** every required prop is present in 100% of that component's occurrences; every optional prop in 30–70%.
- **Nesting:** every layout type holds every child group at least 5 times.

## How to produce the ground truth

1. **`spec.py` as the single source of truth.** Read `dyui.catalog()` and each class's `model_json_schema()` to produce the coverage matrix, enums, required/optional props, and the wrong-name blocklist.
2. **Seeds.** Each seed fixes a category, a policy row, a coverage cell, a domain (about 25 domains, each ≤ 8%), an app persona, a header, turn count, user style and language (about 10% non-English prose with English JSON keys and enums). **Generate all data in code** (numbers, rows, tool results, URLs) so the ground truth is known exactly.
3. **Draft the reference answers** with a strong model that is given the full catalog, the policy table and the category brief. Write 3 hand-made gold examples per category first, and generate 1–4 candidates per seed.
4. **Hard gates** (a failing candidate is discarded):
   - `dyui.genui.parser.parse_text(reply, catalog)` returns no `ComponentError`, using the item's effective catalog (built-ins, restricted by header, plus custom classes).
   - Components are inside the header's allowed set; no block in J, `[dyui off]` or no-component items.
   - Prose before the first and after the last block is non-empty, with no filler phrases.
   - All JSON is single-line; no HTML; no blocklisted names or props.
   - Grounding: every number, name and URL in a block appears in the user, tool or history context.
   - Edits (F): values outside the requested change are byte-identical to the history block.
   - Actions (E): the follow-up's action name exists in the previous component and the payload matches the table above.
   - Limits: ≤ 3 blocks, ≤ 6 components, `quick_replies` ≤ 4 options.
5. **Judge pass.** A strong model scores survivors 1–5 on policy fit, prose usefulness, concision and correctness, and realism of the user turn. Keep only ≥ 4. Calibrate the judge on a hand-written gold set until it agrees with you ≥ 90%.
6. **Human verification.** Because this is ground truth, a human reviews the items, not just a sample. Render items through the real `NodeView` and read them. If something is wrong, fix the generator or policy, not single records. Deduplicate with MinHash over the user turn plus component sequence.
7. **Splits and holdouts.** Use held-out domains, the 60 held-out custom components, and header combinations that are not reused across the set. Record `dyui==1.3.0` and the `spec.py` hash in the dataset manifest.
